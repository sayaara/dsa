# Run Diagnostics and Data Reliability 1.0 (Phase 3)

This document records the scope delivered in #1391 Phase 3: completing run-diagnostics visibility without adding configuration, and backfilling historical troubleshooting information into the backend context snapshot, so a self-hosted deployment can locate a problem quickly.

## Scope of this round

- The history report detail gains a collapsed-by-default "run diagnostics / data reliability" section. After #1523 the Web display title became "run diagnostics / run status", while the historical stage titles are unchanged.
- The task panel shows collapsed trace information for an in-flight task, which makes it easy to correlate with backend logs, SSE, and the history report diagnostics.
- History reports fetch the diagnostic summary through a read-only endpoint:

```http
GET /api/v1/history/{record_id}/diagnostics
```

- If a synchronous analysis response already carries `diagnostic_summary`, the frontend can display it directly without an extra request to the history endpoint.
- The diagnostics panel can copy the redacted `copy_text` generated by the backend, for use in an issue or during deployment troubleshooting.
- After saving history, the analysis path backfills task, provider, LLM, and notification diagnostics into `context_snapshot.diagnostics`, and the history diagnostics endpoint aggregates them into one user-readable summary.
- The home page's run-flow panel reuses the same RunFlowSnapshot contract to show the active task, the completed report, and the market review. An active task appends events in real time through an optional incremental event on the task SSE, and refetches the snapshot after completion or a disconnect to guarantee eventual consistency.

## Real-time run-flow increments

Run-flow increments add no separate SSE endpoint and continue to reuse:

```http
GET /api/v1/analysis/tasks/stream
```

Compatibility contract:

- The event type is still `task_progress`.
- The existing task payload fields are unchanged.
- When a progress update originates from run diagnostics, an optional `flow_event` field may be appended; older clients can simply ignore it.
- `flow_event` uses the same redacted event structure as `RunFlowSnapshot.events[]`: `id`, `timestamp`, `severity`, `type`, `node_id`, `title`, `message`, `metadata`.
- An active task may append real-time `provider_run_started` / `llm_run_started` events. They exist only to render the running card, and once complete the `provider_run` / `llm_run` result event with the same `node_id` overrides the status; historical diagnostics still reflect the final result.
- The backend TaskQueue keeps only the most recent N run-flow events per active task, which prevents unbounded memory growth. The complete history still comes from `context_snapshot.diagnostics` and the historical RunFlowSnapshot.

Example (the `title` and `message` values are the live runtime strings):

```json
{
  "task_id": "3f87...",
  "trace_id": "3f87...",
  "stock_code": "600519",
  "status": "processing",
  "progress": 64,
  "message": "LLM 正在生成分析结果",
  "flow_event": {
    "id": "flow_0002",
    "timestamp": "2026-06-08T22:30:24",
    "severity": "success",
    "type": "llm_run",
    "node_id": "llm_analysis_1",
    "title": "LLM 成功",
    "message": "LLM deepseek-chat 成功"
  }
}
```

The run-diagnostics recording functions trigger the event sink fail-open after a provider, LLM, history-save, or notification record has been written to the in-memory diagnostics successfully. A sink failure only logs a warning and never changes the success or failure verdict of the analysis, the save, or the notification.

News intelligence search follows the same provider diagnostic semantics: `SearchService.search_stock_news()` records each attempt against Tavily, SearXNG, Bocha, Brave, and other search providers as `data_type=news_search`, along with the post-filter result count, cache hits, and failure reasons. When several search providers are tried in sequence, the Web run-flow main diagram aggregates them into a single news node by default, the card shows the provider chain and its status, and the node detail shows success/failure counts and fallback/retry counts. For troubleshooting, that aggregate node can be expanded to inspect each individual provider attempt.

The data-source lane in the run-flow topology is ordered by node start time first. A provider or LLM node that has only an end time and a duration derives `started_at` from `ended_at - duration_ms` and shows the start time on its card. A node with no usable time keeps its original display order as a fallback. The main diagram expresses the flow "entry -> data sources -> ContextPack -> LLM -> save/notify"; the complete troubleshooting detail stays in the event stream, the node details, and the expanded state of an aggregate node.

The Web run-flow main diagram uses an internal frontend display model and does not change the backend `RunFlowSnapshot` contract:

- Provider attempts are aggregated into data-source nodes by `metadata.data_type`, for example real-time quotes, daily bars, and news.
- `context_block_*` nodes are collapsed into the `ContextPack` detail by default, which avoids interleaving them with provider attempts in the data-source lane.
- Clicking an aggregate node shows an attempts table in the detail area; after clicking "expand attempts", that group's child provider nodes return to the topology.
- The event stream still shows every event. An event's associated node maps to whichever node is currently visible: the aggregate node when collapsed, and the specific attempt when expanded.
- Topology edges use a multi-port strategy: the horizontal main flow uses the left and right ports, an up/down relationship within one lane goes bottom to top, and fallback and retry continue to be expressed with a text label and a dashed style.

## Run-flow API

```http
GET /api/v1/analysis/tasks/{task_id}/flow
GET /api/v1/history/{record_id}/flow
```

- Both endpoints return the same `RunFlowSnapshot` contract.
- When an active task has no diagnostics, a skeleton flow is returned rather than fabricated provider or LLM events.
- When an active task already has recent `flow_event` entries, the snapshot returns those real events and can synthesize temporary nodes from the node metadata inside them.
- A completed history builds the full topology from `context_snapshot.diagnostics` and `analysis_context_pack_overview` first.
- Market review history records use `code=MARKET` and `report_type=market_review`, and also go through `/history/{record_id}/flow` and the Web run-flow panel, with no separate UI branch.
- `cancel_requested` and `cancelled` are valid run-flow states; a user cancellation must not be mapped to `failed`.

## The run-flow view

The run-flow view is a visual troubleshooting entry point layered on top of the run-diagnostics summary. It connects an analysis from trigger, through data fetching, ContextPack assembly, and LLM generation, to saving and notification. It does not replace the summary's `copy_text`; it organizes the same redacted diagnostic evidence into nodes, edges, events, and summary metrics, so a degraded or failing step can be located quickly from the Web home page.

The backend provides two read-only snapshot endpoints:

```http
GET /api/v1/analysis/tasks/{task_id}/flow
GET /api/v1/history/{record_id}/flow
```

- `tasks/{task_id}/flow` targets active tasks. While the task is still in the in-memory queue, the current task snapshot is returned first; once it has finished, historical diagnostics can be read by the same `task_id`/`query_id`. With no diagnostics, a skeleton flow is returned rather than fabricated provider, LLM, or notification events.
- `history/{record_id}/flow` targets history reports and accepts either the history record's primary key ID or a resolvable `query_id`. Ordinary single-stock analysis and `MARKET/market_review` market review share the same `RunFlowSnapshot` contract.
- When a single-stock analysis is triggered from the same page, the single-stock flow can generate or reuse the day's market context on demand. That is not a separate single-stock analysis step but prompt background generation. The background saves that market context under its own `market_context_*` query_id with `scope=daily_market_context`, which avoids sharing a query_id with the single-stock report.
- For compatibility with mixed diagnostics written earlier, the run flow applies a low-risk filter by report type when reading history: a `MARKET/market_review` record hides single-stock quote, daily-bar, technical, fundamental, and chip provider nodes, while a single-stock record hides market news searches before the first single-stock quote and market save/notify nodes before the first single-stock LLM call.
- When notification is skipped or unconfigured, `attempts=0` is allowed and the run flow shows it as skipped, so `/flow` no longer returns 500 because of a Pydantic validation failure.
- The snapshot's top level contains `summary`, `lanes`, `nodes`, `edges`, `events`, and `generated_at`. Node status uses `pending/running/success/failed/degraded/fallback/timeout/cancel_requested/cancelled/skipped/unknown`, and the user-cancellation states are never mapped to `failed`.
- For older history, a missing `context_snapshot.diagnostics`, or insufficient evidence, the backend returns `unknown` or skeleton nodes; the Web renders them as empty or unknown, which does not affect reading the report detail.

Web entry points:

- The home page's active task card offers a run-flow entry; opening the drawer fetches the task snapshot by `task_id`.
- The history report summary and the run-diagnostics section offer a run-flow entry; opening the drawer fetches the history snapshot by history record ID.
- The panel shows the summary, the basic topology, the event stream, and node details. Complex topology aggregation, real-time incremental events, and layout polish continue to converge in later stages.

Redaction and compatibility boundary:

- The run flow reads only existing task information, historical results, and the low-sensitivity diagnostic fields in `context_snapshot.diagnostics`. It adds no configuration options, changes no database structure, and migrates no old history.
- `model`, `provider`, and `fallback_model` are used only to display the call information actually diagnosed; they take no part in model selection, request routing, base URL resolution, or configuration saving.
- `metadata`, error messages, and local paths are trimmed and redacted by the backend, which avoids exposing API keys, tokens, cookies, webhooks, prompts or raw responses, proxy headers, and local absolute paths.
- To roll back, remove the Web entry points and the query paths; the new read-only snapshot endpoints do not change the success or failure semantics of the existing analysis, history, notification, or diagnostic-summary endpoints.

## Status labels

Overall status:

- `normal`
- `degraded`
- `failed`
- `unknown`

Component status:

- `ok`
- `degraded`: degraded after a recent failure
- `failed`
- `unknown`
- `not_configured`
- `skipped`

## Interaction boundaries

- The diagnostics section is collapsed by default, so it does not crowd out the report's main content.
- The first screen shows only the overall status, the primary cause, and the necessary trace information.
- Component status and advanced JSON fields sit inside the expanded area, and the advanced fields collapse a second time, which avoids information overload.
- Older reports, an endpoint failure, or insufficient evidence show `unknown` without affecting report reading.

## Compatibility boundary

- This round adds no `.env` options, changes no database structure, and introduces no data migration.
- The Web only consumes the optional fields and read-only diagnostic endpoints added in Phases 1 and 2. The backend completes diagnostic persistence and refresh in `src/core/pipeline.py`, `src/services/run_diagnostics.py`, `src/storage.py`, and `src/services/history_service.py`, and exposes a readable endpoint through `api/v1/endpoints/history.py`.
- The backend change covers task orchestration, post-save backfill, historical diagnostics queries, and notification-result diagnostic records. Those paths only append a diagnostic snapshot and summary to `context_snapshot.diagnostics`; they do not change the main analysis flow, the success/failure semantics of notification delivery, or the main fields of a history report.
- The copy text is generated and redacted by the backend; the frontend only displays and copies it.
- Desktop reuses the Web build output, with no separate change to the Electron main process or the packaging scripts.
- Runtime configuration, model, provider, and base_url compatibility semantics are unchanged: apart from the diagnostic persistence path, provider priority, LiteLLM routing, runtime cleanup, and configuration-fallback logic are untouched.
- Compatibility rules for older history and older configuration are unchanged: the optional fields added to the historical diagnostics query do not affect parsing of existing history query responses. To roll back, remove this round's display and the related frontend query paths, or restore the model and configuration following the existing guide.
- Rollback strategy: revert the frontend display and query entry points first. To isolate the new path entirely, revert this round's PR (after which history records keep their original responses and the new diagnostics endpoint is simply no longer surfaced in the Web).

### Clarifying the structured detection

This round's review triggered structured detections for external model/API compatibility and runtime configuration migration risk. After review:

- Model names / providers / base URLs: this round adds, replaces, and reorders no model name, provider, base URL, channel, or fallback default, and does not change the resolution precedence of `LITELLM_MODEL`, `AGENT_LITELLM_MODEL`, `VISION_MODEL`, `LITELLM_FALLBACK_MODELS`, `OPENAI_*`, `GEMINI_*`, `ANTHROPIC_*`, or `DEEPSEEK_*`.
- SDK and dependency defaults: this round modifies no `requirements.txt` or `package.json` dependency constraint, and no LiteLLM/OpenAI-compatible call default. External sources remain the official documentation and current pinned-dependency notes already recorded in `docs/llm-providers.md` and `docs/LLM_CONFIG_GUIDE*.md`.
- Pre-save cleanup and configuration migration: this round triggers no migration, cleanup, deletion, or write-back policy change for `.env`, the Web settings page channels, the desktop user-data directory, Docker runtime configuration files, or older stored configuration.
- The only actual runtime change this round writes the existing analysis trace, the provider/LLM/notification results, and redacted error summaries into `context_snapshot.diagnostics`, and displays them through a read-only history endpoint and a collapsed-by-default Web panel. A failed diagnostic record is handled fail-open and never changes the success or failure verdict of an analysis or a notification.
- This is therefore a structured-detection false positive resolved by documentation. There is no new official source, old-configuration migration step, or provider fallback path to execute. To roll back, follow the strategy in this section and remove the diagnostics display and query entry points; the model and runtime configuration recovery path is unchanged.
